# Hbox CSS architecture

Hbox uses three CSS layers with strict ownership.

## global.css

global.css already exists and is maintained by Hbox.

It contains design-neutral structural primitives, including:

* reset and normalization
* accessibility helpers
* containers
* sections
* grids
* rows and columns
* stacks and clusters
* responsive layout helpers
* card structure
* media frames
* sidebar layouts
* common alignment and sizing utilities

Never generate, reproduce, replace, or modify global.css.

Prefer existing global.css classes whenever they express the required structure.

Examples include:

* container
* container-narrow
* container-wide
* container-full
* section
* section-small
* section-large
* grid
* grid-2
* grid-3
* grid-4
* grid-auto
* grid-equal
* row
* column
* stack
* cluster
* split
* sidebar-layout
* switcher
* cover
* reel
* frame
* frame-square
* frame-portrait
* frame-landscape
* frame-wide
* overlap
* card
* card-body
* card-media
* card-actions

Do not recreate an equivalent layout class in generated CSS when an existing global.css class can express it clearly.

Use semantic project-specific classes in addition to global classes when visual styling or page-specific behavior is required.

Example:

<div class="container">
  <div class="grid grid-3 services-grid">
    ...
  </div>
</div>

In this example:

* container and grid-3 come from global.css
* services-grid is available for page-specific refinements

* standard text colors

* unique decorative artwork
* one-off background placement
* section-specific responsive behavior

page_css must contain only CSS source.

Do not include style tags.

# CSS ownership decision

For every generated CSS rule, ask:

“Would changing this rule reasonably affect multiple pages?”

If yes, place it in design_css.

If no, place it in page_css.

Do not place the same rule in both files.
Do not duplicate design tokens between design_css and page_css.
Do not move page-specific positioning into design_css merely because it uses colors or typography.
Do not move reusable card, button, navigation, or heading styling into page_css merely because this is the first page using it.

Use CSS custom properties in design_css for recurring design values.

Page CSS may consume those variables but should not redefine them unless a page-specific override is genuinely required.

page_html is required and must be a non-empty string.

page_html must:

* be a complete Hbox page template
* contain a complete HTML document
* include an html element with a valid, non-empty lang attribute inferred from the page content
* use semantic HTML

* use page-specific classes defined in page_css
* reproduce the design specification as closely as possible
* remain readable and maintainable
* follow the asset filename and public URL contract below

page_html must not:

* use a frontend framework

* generate arbitrary utility classes that duplicate global.css

{{ content }} is reserved for blogpost templates and must never appear in page_html.

Hbox is responsible for loading global.css, design.css, and the page-specific stylesheet. Do not inject generated CSS into page_html or reference any of these files by link or href.

# Shared partial rules

The shared partial rules supplied with this request are binding.

header_html and footer_html must always be present in the returned JSON, but their values depend on those rules.

When a partial already exists:

* return null for its field
* do not recreate it
* include the existing partial from page_html as instructed

When a partial is missing:

* return a non-empty HTML string for its field
* generate only that missing partial
* include the partial from page_html as instructed

Never return an empty string for header_html or footer_html.

Shared partial HTML must:

* contain semantic markup
* contain no style elements
* contain no inline styles
* use global.css structural classes where appropriate
* use reusable visual classes whose styling belongs in design_css
* avoid page-specific classes unless the partial itself genuinely requires them

Header and footer visual styling belongs in design_css, not page_css.

# SVG rules

Every meaningful icon required by the design must either:

1. be an inline SVG in the relevant HTML field, or
2. reference one concrete SVG asset from assets_manifest

Use inline SVG when:

* the icon uses currentColor
* the icon inherits text color
* the icon changes color on hover or focus
* the icon belongs to a button
* the icon belongs to a card
* the icon belongs to a stat
* the icon belongs to a badge
* the icon belongs to navigation
* the icon belongs to a text link

Never use an img element for an SVG that relies on currentColor. Parent CSS color does not style an externally loaded SVG image.

Use external SVG files with img only for:

* logos
* client logos
* brand marks
* large standalone vector illustrations
* fixed-color SVG artwork

Every external SVG must have its own assets_manifest entry.

Do not bundle multiple icons into one SVG.
Do not create icon sheets.
Do not create sprite sheets.
Do not create SVG collages.
Do not create SVG grids containing several independent assets.

Each SVG asset must represent exactly one visual asset.

# Asset manifest contract

assets_manifest must be a JSON object, not a string.

It must have exactly this shape:

{
"assets": [
{
"filename": "string",
"kind": "image | svg | css_generated",
"description": "string",
"generation_prompt": "string",
"size": "1024x1024 | 1024x1536 | 1536x1024 | auto | null",
"svg_code": "string"
}
]
}

Implement every asset required by the design specification. Include every local
file-backed visual asset referenced directly by page_html, header_html,
footer_html, design_css, or page_css. Do not hotlink remote images or SVGs.

If the design requires no assets, return an empty assets array.

Every manifest item must include:

* filename
* kind
* description
* generation_prompt
* size
* svg_code

description must be a non-empty explanation of the asset's purpose.

Each asset must represent exactly one visual asset.

Do not combine multiple icons, images, logos, illustrations, or UI elements into one asset.

## Asset filenames and public URLs

For image and SVG assets, filename is a safe path relative to the public images
directory. It may contain subdirectories, but it must not:

* be absolute
* begin with a slash
* begin with images/ or public/images/
* contain . or .. path components
* contain backslashes, a query string, or a fragment

For example, use hero.jpg or case-studies/hero.jpg as the manifest filename.

Hbox installs image and SVG assets beneath public/images/. Reference every such
asset from page_html, header_html, footer_html, design_css, and page_css using
its public URL:

`/images/{filename}`

For example, a manifest filename of hero.jpg has the public URL
/images/hero.jpg. A manifest filename of case-studies/hero.jpg has the public
URL /images/case-studies/hero.jpg.

Never use hero.jpg, images/hero.jpg, or public/images/hero.jpg as the public URL.
In CSS, use url("/images/{filename}").

CSS-generated assets are not file-backed and must not be referenced through a
URL or img element.

Every file-backed asset in assets_manifest must be referenced by at least one
returned HTML or CSS field. Do not generate unused file-backed assets.

## Raster assets

Use kind = "image" for complex raster artwork or photography.

Use raster images for:

* photography
* detailed illustrations
* complex textures that cannot reasonably be recreated with CSS
* detailed hero artwork

Do not use raster images for:

* simple gradients
* solid backgrounds
* borders
* shadows
* basic geometric shapes
* simple decorative lines
* standard UI icons

For image assets:

* svg_code must be an empty string
* generation_prompt must be detailed enough to generate the intended visual
* size must be "1024x1024", "1024x1536", "1536x1024", or "auto"; it must not be null
* filename must end in .png, .jpg, .jpeg, or .webp

## SVG assets

Use kind = "svg" for external logos, brand marks, fixed-color icons, and standalone vector illustrations.

For SVG assets:

* svg_code must contain complete, valid SVG XML
* generation_prompt must describe the intended asset
* filename must end in .svg
* size must be "auto"

Do not merely describe the SVG.
Generate the actual SVG source in svg_code.

## CSS-generated assets

Use kind = "css_generated" only when the design specification explicitly treats a named visual as an asset but it should be rendered entirely through CSS.

For CSS-generated assets:

* filename must be a non-empty descriptive identifier such as hero-glow; it is not a path or public URL
* svg_code must be an empty string
* generation_prompt must explain that the visual is CSS-generated
* size must be null
* do not reference the item through an img element
* the actual CSS must appear in design_css or page_css according to ownership

Do not add trivial CSS decorations to assets_manifest unless the design specification explicitly identifies them as assets.

# Maintainability

Prefer:

* semantic HTML
* existing Hbox structural classes
* predictable BEM-like or component-oriented names
* reusable component classes
* concise selectors
* CSS custom properties
* low selector specificity
* clear ownership between design_css and page_css

Avoid:

* generated class-name noise
* deeply nested selectors
* IDs used for styling
* !important
* excessive absolute positioning
* excessive wrapper elements
* duplicate declarations
* arbitrary magic numbers when a reusable variable is appropriate
* broad selectors in page_css that could leak into other pages

Use absolute positioning only where the design genuinely requires overlap or layering.
